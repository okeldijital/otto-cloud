### 1.2 Diagnosis

The migration chain was **broken in two places**, not one:

1. **`20260619000001_add_release_workspace_models`** existed in source but was
   never applied, and was **not self-contained**: it altered the `workspaces`
   table (added `uq_workspaces_release_id`, FK constraints) but never *created*
   `workspaces`. Because the shadow database is rebuilt from scratch by replaying
   the migration files, the missing `workspaces` table caused shadow
   reconciliation to fail — blocking `prisma migrate dev`.

2. **A broader, systemic drift** was uncovered while reconciling: the IAM /
   multi-tenancy schema (`tenants`, `roles`, `permissions`, `teams`,
   `team_members`, `invitations`, `tenant_users`, `user_roles`,
   `role_permissions`) and the `tenant_id` column added to ~50 tables were
   present in `schema.prisma` and in the development database, but were **never
   captured in any migration**. `0001_initial` creates 66 tables and does not
   include these. The migration history could therefore never reproduce the full
   schema from a clean clone.

### 1.3 Verification method

- `prisma migrate diff --from-migrations prisma/migrations --to-schema-datamodel prisma/schema.prisma` → **empty** (the chain now produces the exact schema).
- `prisma migrate diff --from-url $DATABASE_URL --to-schema-datamodel prisma/schema.prisma` → **empty** (live DB matches schema).
- `prisma migrate status` → `Database schema is up to date!`

## 2. Repair Summary

### 2.1 Root cause

Schema evolution (Workspace Architecture, IAM, multi-tenancy) happened via
direct database changes / `prisma db push` rather than through migration files.
As a result:
- `20260619000001` was committed without `workspaces` being created first.
- The IAM / `tenant_id` changes were never turned into migrations.

This left the migration history unable to replay to the current schema, breaking
shadow-database reconciliation and `prisma migrate dev`.

### 2.2 Repair method

1. **Fixed `20260619000001`** to be self-contained: prepended
   `CREATE TABLE "workspaces"` (with PK, indexes, and the `uq_workspaces_release_id`
   unique index) so its FK references resolve when the chain is replayed from
   scratch. Also standardized all 14 of its FK constraints to Prisma's default
   `ON DELETE CASCADE ON UPDATE CASCADE` so a fresh replay matches the schema
   exactly (no residual drift).

2. **Created `20260717140000_repair_workspace_tables`** — the exact Prisma diff
   between the post-`20260619000001` database state and the schema. It tightens
   nullable columns to `NOT NULL`, creates the remaining workspace tables
   (`workspace_templates`, `workspace_template_sections`, `workspace_template_statuses`,
   `workspace_members`, `workspace_timeline_events`, `workspace_files`,
   `workspace_notifications`, `workspace_deliverable_dependencies`,
   `workspace_template_fields`, `workspace_dynamic_fields`), and adds their
   indexes + foreign keys (including `workspaces.template_id → workspace_templates`).

3. **Created `20260717141000_repair_iam_tenant_tables`** — the exact Prisma diff
   for the IAM / multi-tenancy gap: adds `tenant_id` to the ~50 tables that need
   it, creates `tenants`, `tenant_users`, `invitations`, `roles`, `permissions`,
   `role_permissions`, `user_roles`, `teams`, `team_members`, and adds all
   indexes + foreign keys.

4. **Rebuilt the database from the chain**: the dev database had been left in a
   partial, untracked state (empty tables, `_prisma_migrations` absent). With no
   data to preserve, all public tables were dropped and `prisma migrate deploy`
   rebuilt the database cleanly from the now-complete 9-migration chain. This is
   the only way to guarantee a self-contained, clone-able history.

All repair DDL was generated by Prisma itself (`migrate diff`), not hand-written,
so it is guaranteed to match the schema.

### 2.3 Remaining risks

- **None for migration integrity.** The history is now complete and replayable.
- The two repair migrations are additive and idempotent with respect to the
  corrected `20260619000001`; they apply cleanly on a fresh clone.
- A new developer cloning the repo and running `prisma migrate deploy` (or
  `prisma migrate dev`) will arrive at a database that exactly matches
  `schema.prisma`. No manual SQL is required.
